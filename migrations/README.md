# migrations/ の規約(スキーマ変更の書き方)

本ディレクトリはスキーマ(**保護領域** — 定款第5条・CLAUDE.md)。以下の規約は
既存 migration に散在する注記(0021 / 0035 など)を1箇所にまとめて明示する
覚え書きであり、**新しい規約を作るものではない**。既存の migration の書き換えは
禁止(追記オンリーの保護領域)。

## 追記オンリー・テーブルの三点セット

追記オンリーを要求するテーブル(仕訳・議事録・決定・stance など)は、初回定義から
次の三点をすべて張る:

1. **行トリガ** `BEFORE UPDATE OR DELETE ... FOR EACH ROW`
   … 通常経路の封鎖
2. **文トリガ** `BEFORE TRUNCATE ... FOR EACH STATEMENT`
   … TRUNCATE の封鎖(PostgreSQL の仕様上、行トリガは TRUNCATE で発火しない)
3. **`REVOKE UPDATE, DELETE, TRUNCATE ... FROM PUBLIC`**
   … 権限層の防波堤

行トリガだけでは TRUNCATE を素通しし、追記オンリーの主張は空手形になる
(0005 ledger・0013 governance の minutes/stances に初期の穴があり、
0018 / 0021 が後追いで塞いだ)。

## REVOKE FROM PUBLIC の位置づけ(A-12 pass4 所見2 の指摘)

`REVOKE ... FROM PUBLIC` は**テーブル所有者ロールには効かない**。現構成では
アプリと同一の `ryza` ロールがテーブルを所有しているため、実弾に至るまで
ロール分離を導入していない本プロジェクトでは実質 **no-op** である。

- **主防壁は文トリガ側**(所有者にも効く)。REVOKE を落とすと外形の防波堤は
  消えるが、実質の封鎖は継続する
- **REVOKE を書き続ける理由**: ロール分離後の統制(将来アプリユーザを所有者と
  切り離す)と、ドキュメント上の意図表明(この列/表は追記オンリー)。
  0021 のコメントと同じ流儀

ロール分離は実弾マネー移行の前提条件として別途扱う(定款第3条・
`ops/reminders.yaml` のロール分離検討リマインダー)。REVOKE の欠落だけを
理由に「保護が弱い」とは判定しない — 主防壁は文トリガ側に張る規約である。

## 命名・番号

- ファイル名は `NNNN_短い説明.sql`(NNNN は連番・ゼロ埋め4桁)
- **既存ファイルの書き換え禁止**(追記オンリー — スキーマは監査対象)。修正は
  常に新しい番号の migration を積む
- 一つのテーブルに対する三点セット(上記)は**同じ migration にまとめる**
  (0026 が market スキーマで初回定義から実践済み)。分割すると受入前の一時状態が
  fail-open で走る
