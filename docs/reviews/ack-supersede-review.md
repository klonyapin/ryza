### 1.4 「不正承継が正当な受容を壊さないか」(審査観点 2 後段)

プローブ 1(縮小)で確認: 不正な supersedes を持つのは**新エントリだけ**であり、旧エントリは
index に残って従来どおり違反を受容する。巻き添え無効化はない。逆に旧エントリの側が不正
(SHA 欠落等)なら新エントリの承継先が不在となり両方効かない — これも fail-safe 方向。

### 1.5 governance.yaml の記述と実装の一致(審査観点 5)

4 条件・fail-safe・毎回の承継注記・陳腐化除外・追記オンリー維持は実装と一致。

## 2. 発見事項

- **低-1(本機構と相互作用する既存の穴): 同一キーの重複エントリによる表示メタデータの差し替えが無開示**。
  `acknowledged_index` は `index[key] = entry` で後勝ち上書きするため、既存エントリと同一
  (commit, paths) のエントリを**追記**すると、報告に出る ack_reason / approval_ref が黙って
  差し替わる(プローブで実証: 注記ゼロ)。governance.yaml の限界注記(低-8)は「書換」を
  想定して「本ファイルが保護領域であること」を担保としているが、追記オンリー規則の文言上
  「同一キーの追記」は禁止列挙(削除・書換)に入っておらず、A-18 も重複を開示しない。
  承継注記そのものは本物のエントリ側から出続けるため承継の隠蔽には至らないが、
  「誰の・どの承認で受容されたか」の表示は差し替え可能。
  **是正案**: 重複キー検出時に notes へ開示(1 行)+運用規則に「同一キーの追記も書換とみなす」を明記。

  **裁定: 採用(本 PR で是正)**。開示にとどめず**後のエントリを無効(受容として効かない
  fail-safe)**とした — 開示だけでは「読まれなければ差し替えが成立する」ため。notes には重複キーと
  両エントリの approval_ref・acknowledged_on・reason を出す。受容自体は先のエントリで従来どおり
  成立するので既存の受容を巻き添えにしない。governance.yaml の追記オンリー規則に「同一キーの
  重複追記も書換とみなし禁止」を明記。テスト2件で固定
  (`test_duplicate_acknowledgement_key_keeps_first_and_discloses`・
  `test_duplicate_key_does_not_leave_stale_note` = 無効化した側が陳腐化として二重に鳴らないこと)。
- **低-2: 実装は supersedes.paths を正規化(順序・重複・空白無視)して照合するが、様式の記述は「逐語で」**。
  実装が寛容な側なので危険はないが、様式どおり書かない承継が成立し得る点で仕様と実装が
  一致していない。どちらかに寄せるべき(推奨: 記述を「集合として一致」に修正)。

  **裁定: 採用(本 PR で是正)**。記述側を実装に合わせた — 様式から「逐語で」を落とし、
  「paths は**集合として照合**する(順序・重複・前後の空白は無視して正規化)」と明記。
  実装を厳格化しなかったのは、承継先の同定に順序・重複の情報は不要であり、厳格化しても
  統制は増えないため(むしろ書式の揺れで正当な承継が落ちる側の害が出る)。
- **低-3: paths がスカラ文字列のとき 1 文字ずつ分解される(既存挙動の継承)**。結果は fail-safe だが、
  開示文言が `(1, p)` のような不可解なキーになる。supersedes に限らず通常エントリでも同じ。
  型検査(list 以外は「無効」として開示)が 2 行で足せる。

  **裁定: 採用(本 PR で是正)**。`_paths_are_list` を追加し、通常エントリ・supersedes 宣言の
  両方でスカラ文字列を「paths はリストであること」として明示的に無効化・開示する。
  テスト2件で固定(`test_scalar_paths_entry_is_rejected_with_clear_note`・
  `test_scalar_supersede_paths_is_rejected_with_clear_note`)。
- **低-4: reminders.yaml の実走記録「violations 1 件」は本 PR のコミット前の計測**。コミット後 HEAD では
  本 PR 自身が 2 件目として鳴る(正しい挙動)。監査証跡としては「PR 自身はマージ承認まで鳴る」
  旨を一言添えるのが正確。

  **裁定: 採用(本 PR で是正)**。審査の追試(2 件)が正しい。reminders.yaml の実走記録を
  コミット後 HEAD の実測に更新し、2 件目が本 PR 自身であること・PR マージコミットの Approved
  トレーラで PR 承継の規則により解消されることを明記した。起草時の記録が計測時点を書いて
  いなかったのが原因であり、以後の実走記録は計測時点(コミット前/後)を添える。
- **低-5: ダイヤモンド承継(複数エントリが同一旧エントリを承継)が仕様に明記されていない**。
  実装は許容し、不一致側が陳腐化として鳴るため隠蔽には使えないが、様式の想定外の形が
  無警告で成立する。禁止するか、許容を明記するか。

  **裁定: 採用 —「許容」を明記(本 PR で是正)**。禁止しなかったのは、保護領域を二度に分けて
  追加すれば正当な運用として自然に生じる形であり、禁止すると承継が使えず元のラチェットに
  戻るため。隠蔽に転用できないことは審査のプローブ 9 と本 PR のテスト
  (`test_diamond_supersede_is_allowed_and_mismatch_rings` — 当たらない側が陳腐化として鳴る)で
  固定した。governance.yaml の承継様式に一文追記。
- **懸念(判定を留保しない・記録のみ): tests/execution/test_demo.py・test_runner.py・test_close.py は
  invariant_tests 未登録のまま**。phase-2 の「暫定の担保」だったテスト群のうち登録されたのは
  test_config.py のみ。実装側 src/ryza/execution/** が保護された今、二段攻撃(先にテストを無承認で
  弱め、後で実装変更を審査に通す)の実装変更側は必ず承認を経るため実害は限定的だが、審査者が
  「テストが緑」を根拠に承認する場面では弱められたテストが審査品質を下げる。登録基準
  (実装から独立した参照の有無)に照らした対象外判断を棚卸し記録に一行残すことを推奨する。

  **裁定: 採用 — 対象外記録ではなく3件とも登録(本 PR で是正)**。実装側を保護した PR の
  自然な完結であり、3件とも登録基準(実装から独立した参照)を満たすため:
  test_demo.py = スリッページ適用後の約定価格・手数料クランプの**手計算の期待値**
  (1001.90 / 998.10 等)、test_runner.py = **原子性と帳簿分離の対照**(仕訳失敗時に executions が
  残らない・運営帳簿への記帳は落ちる・buy/sell 以外はブローカーへ出さない)、
  test_close.py = NAV の**手計算値**(9,999,936 等)。各行に適合理由を付して登録した。
