## §1 適用範囲の分析(静的読解)

検出ロジックの構造(a18.py `check_reminder_tampering`、diff main..HEAD +2348〜+2705 相当):
`_rev_list(since..HEAD)` 全コミット走査 → `has_approval_trailer` で存在検査(トレーラ有りは分母からも除外)→ 第1親との blob 比較 → `_reminders_index` で id 突合 → before が pending のエントリのみ3分岐(削除 / pending のまま期日後ろ倒し / 終端遷移+証跡判定)。

### 1a. 2コミット分割遷移 — **検出対象外(重要度: 重要)**

- before_status が `pending` でないエントリは無条件に `continue`(コード: `if before_status != "pending": continue`)。また after_status が pending でも終端4種でもない**中間値**(例 `paused` / `on-hold` / `wontfix` — 語彙は `_REMINDER_TERMINAL_STATES = {done, fired, superseded, cancelled}` の4語のみ)への遷移は、削除でも期日変更でも終端でもないためどの分岐にも該当せず無音。
- 帰結1: **単一コミットで `pending` → 任意の非終端・非 pending 文字列**(`paused`、`completed`、`closed`、typo を含む)に書き換えると、証跡要求なしにエントリを実質停止できる。weekly ジョブが pending のみを発火対象とするなら統制上は終端化と等価。
- 帰結2: **コミット1で pending→中間 status、コミット2で削除または done 化**すると、コミット1は上記により無音、コミット2は before が pending でないため無音。同一 PR 内の2コミットで完結する回避経路であり、main の first-parent 視点でも合成 diff は1回の遷移にしか見えないが、本検査はコミット単位のペア比較なので追跡が切れる。
- 評価: 仕様(T-020 §検査仕様「`status: pending` のエントリ」)には忠実だが、status 語彙がスキーマで閉じていない(reminders.yaml に status の許容値バリデーションが無い)以上、「未知の status = 検査から外れる」は fail-open。終端集合のホワイトリスト方式ではなく「pending 以外への遷移すべてに証跡を要求」(pending 残留のみ無音)とすれば閉じた。

### 1b. ハンク→エントリ帰属と証跡判定の粒度

- 帰属機構: `git diff -U0 parent sha` のハンクヘッダの**変更後行番号**を、変更後テキストの `- id:` 行位置から作った閉区間(`_entry_line_ranges`)と重なり判定(`_hunks_touching_entry`)。-U0 なのでコンテキスト行は混入せず、**別エントリの変更ハンクは行番号帰属で正しく分離される**(同一コミットで複数エントリを変更しても、エントリ A の判定にエントリ B のハンクは使われない — §7 で動的確認)。regex でハンク本文から id を探す方式より頑健で、実装者申告の「行番号ベース」への変更は妥当(§3)。
- ただし証跡判定は「当該エントリ範囲に重なる**全ハンクの生テキスト**」に対する `_REMINDER_EVIDENCE_RE` 検索であり、以下が対象外化の条件になる:
  - **同一エントリ内の無関係な既存参照の巻き込み(重要度: 中)**: 終端遷移と同時に、同エントリの body 等「参照文字列(URL・#番号・hex)を含む既存行」を1箇所でも編集すると、削除側(`-`)行の参照がハンク生テキストに現れ証跡ありと判定される。本台帳の body は出典 URL・Issue 番号を高頻度で含むため、意図的な回避は1行の些末な編集で足りる。生テキスト判定という仕様自体に内在する限界(T-020 が明示的に選んだ方式)。
  - **並べ替えとの複合(重要度: 中)**: エントリ並べ替え単独は id 突合により無音で正しいが、並べ替え+終端遷移を同一コミットで行うと、移動により当該エントリ全行が追加行としてハンクに入り、body 内の既存参照が証跡と誤認され得る。
  - **id 行が regex に合わない場合は fail-closed(問題なし)**: `_ID_LINE_RE` は非クオート id のみ照合。id をクオートすると範囲が引けず hunk="" → 証跡なし扱い(誤検出方向であり回避には使えない)。
- `#\d+` は `#` 直後に数字を要求するため、日本語コメントの通常表記(`# 2026-08-04 完了`)は PR 番号と誤認されない。一方 **7〜40桁の連続数字はすべて hex として証跡成立**する(例 `20260804`)— §2 で詳述。

### 1c. YAML 構造変化での追跡

- `_reminders_index` は doc 非 dict / `reminders` 非 list / エントリ非 dict / id 欠落・非文字列をすべて None → unparseable 所見(fail-closed)。構造の組み替えで検査を「静かに」外すことはできない — 開示に落ちる。妥当。
- 重複 id は dict 構築で後勝ちになるが、原本 pending エントリを残したまま同 id の done エントリを追記する細工は、after 側 status=done かつ原本範囲にハンク無し → `terminal_without_evidence` として検出される(偶然だが fail-closed 方向)。
- `reminders:` キー自体の削除(`doc.get("reminders") is None` → `{}`)は「全 pending エントリの削除」として全件所見になる。妥当。
- **ファイル削除・改名は `after is None` → `file_removed` 所見**。仕様どおり。

### 1d. マージコミット(evil merge)— **検出対象外(重要度: 重要)**

- touched 判定が `git diff-tree --no-commit-id --name-only -r <sha>`(`-c`/`--cc`/`-m` なし)。git はマージコミットに対してこの形式では**パス名を出力しない**ため、マージコミットは常に `path not in touched` → スキップ(§7 で動的確認)。
- コード内コメントは「evil merge は A-18-1 の担当」と主張するが、**A-18-1 の `--cc` 検査は protected_areas パターンに一致したファイルのみ**が対象(`check_protected_commits`: `match_protected(files, patterns)` で不一致は continue)。ops/reminders.yaml は保護領域外なので A-18-1 は拾わない。つまり「PR のコンフリクト解消を装ってマージコミット自身で pending→done を持ち込む」経路は**どの検査にも載らない**。コメントの根拠が事実と異なる点も含め要修正。

### 1e. Approved トレーラの存在検査のみで対象外化 — **検出対象外(重要度: 重要)**

- 対象外条件が `has_approval_trailer`(**存在検査のみ**、docstring 明記)。コメントは「トレーラの参照有効性は A-18-1 の担当」とするが、A-18-1 が参照を実在照合(`trailer_approves` / decision 突合 / PR 実在確認)するのは**保護領域に触れたコミットだけ**。reminders.yaml のみに触れるコミットに架空の `Approved: <実在しない参照>` を書けば、A-18-9 は分母からも外し(checked にすら入らない)、A-18-1 は見ず、どこにも開示されない。偽トレーラによる完全バイパス。
- A-18 は同種の穴(架空 PR 番号)を「重大-1」として PR 実在照合で塞いだ経緯があり(a18.py の GitHub PR 実在照合節)、本検査だけ存在検査で通すのは既存の設計判断と不整合。最低限、トレーラ付きは「対象外」でなく「トレーラ付きとして件数開示」(checked と分離)にするか、conn/pr_verifier がある実行では `trailer_approves` を通すべき。

### 1f. 期日後ろ倒し検出の境界

- `_reminder_deadline` は `conditions[].date_after.date` のうち **isinstance(d, str) の最大値**。以下は対象外:
  - **クオート外し(重要度: 中)**: YAML で `date: 2027-09-01` と非クオートで書くと safe_load は `datetime.date` を返し、`isinstance(d, str)` 不成立 → a_date=None → `b_date and a_date` 偽 → 無音。後ろ倒しをクオート外しと同時に行うだけで検出を外れる。str() 正規化で閉じられる。
  - **date_after 条件自体の削除・type 書き換え(重要度: 中)**: 条件を消す/`type` を別語に変えると dates 空 → None → 無音。発火条件の削除は期日変更より強い改変だが対象外。
  - 複数 date_after の max 比較は、条件が AND 評価である前提では保守的で妥当。ISO 形式の辞書式比較は現行コーパス(ゼロ埋め ISO)では正しい。
- pending → pending 以外への遷移と期日変更を同時に行った場合は期日検査に入らないが、遷移側の検査(1a の穴を除く)に落ちるため単独論点としては軽微。

### 1g. その他の対象外(仕様どおり・妥当と評価)

- 新規追加のみ(before=None)・エントリ追加: 無音。登録の逆インセンティブ回避という設計意図に整合。
- 前倒し: 無音。統制を弱めない方向で妥当。
- ルートコミット(親なし): 対象外。since_commit 以降にルートは現れないため実害なし。
