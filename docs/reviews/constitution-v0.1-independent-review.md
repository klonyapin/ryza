骨格(専決事項列挙+広範授権、執行点原則、機械可読統制テーブル)は制度調査に忠実で健全である。しかし「執行点に紐付かない条文は置かない」と自己宣言する文書としては、現時点で実効している執行点が 8 統制中 3 つ(schema 2+gate 1)しかなく、かつ保護領域のパス列挙に迂回可能な穴が複数ある。

## 懸念事項(重大度順)

### 懸念1(重大): パス列挙型保護は「新規ファイル」で合法的に迂回できる

シナリオ: **S1** `migrations/0013_x.sql` を新規作成し帳簿分離の book_id 制約を DROP(0012 以外の migrations は保護外・層帰属も未定義で design_lead 自己承認可能)。**S2** killswitch.py は保護されるがコマンド登録元の `bot/main.py`・`approvals.py` は保護外 — 登録を外せば Kill Switch は保護パス無傷のまま死ぬ。**S3** `ops/deploy-bot.sh` を書き換え未承認ブランチからデプロイ — 稼働コード=承認済みコードの検証が制度上どこにも存在しない。
修正提案: パス追加に加え、「振る舞いの不変条件テスト」(帳簿間参照禁止・KS 経路存在・ゲート順序)を tests/ に置きテスト自体を保護領域に。デプロイは main の承認済み SHA からのみをスクリプトで強制。

### 懸念2(重大): 発見統制偏重 — 自動執行システムでは事後検知は遅すぎる

A-13 は未実装・CI ランナー不在で、enforcement: ci の統制も「手元でテストを実行した場合のみ」効く紳士協定。修正提案: 保護領域は予防統制(ブランチ保護+CI 承認チェック)へ転換し A-13 は二重底に。少なくとも実弾移行を「予防統制の稼働」に条件付ける一文を第5条に。

### 懸念3(中): 機械可読版が定款と食い違い、齟齬解決規則が逆向き

L2 `draft_by` のフィールド値が定款第4条の表と矛盾。L3/L4 の glob が上位文書・governance.yaml 自身を包含し層帰属が多義。「齟齬は本書が正」というが機械が読むのは YAML の方。修正提案: per-doc の権限構造化+「最上位一致優先」明記+glob 重複検出テスト。

### 懸念4(中): 委任先文書の陳腐化を定款が継承している

05-governance は投資委員会・CIO レポートが「四半期」のままで IPS v1.3 の月次制と不整合。第7条の「charter に列挙された行為のみ」は charter 未整備の現在、権限の外延が空定義。修正提案: 05 の頻度整合を同時決裁に。第7条に経過規定。

### 懸念5(軽): 盲検レビューの手続き矛盾

一人+AI 組織で起草者秘匿は不可能。「盲検=起草者の選好・経緯を伝えない(プロンプト分離)」に定義を狭めるべき(議論規約3 への参照に置換)。

## 反対意見書 — この定款が間違っている場合の理由トップ3+代替案

1. **保護の単位が「ファイル」なのが誤りである可能性**。守るべきは帳簿分離・KS 経路・ゲート順序という振る舞い。代替案: 不変条件テスト+ブランチ保護を一次統制、パス列挙は補助インデックスに格下げ
2. **文書階層モデルにシステム実体が乗らない**。Ryza の「規程」の大半は src/・migrations・クラウド設定というコード。代替案: 「変更対象4類型(文書/設定/コード/インフラ)×承認権限」のマトリクスに再設計
3. **批准のタイミングが早すぎる可能性**。実効統制 3/8 の段階で最上位文書を発効させると「宣言だらけの定款」という形骸化を最上位からやることになる。代替案: A-13-1 と CI ゲートの最小実装を批准の前提条件に(条件付き承認はこの折衷)

## 良い点

- 執行点原則+「宣言」の明示マークは形骸化を検出可能にする誠実な設計
- 専決事項の明示列挙は簡潔で漏れが少なく、IPS「起票も代表のみ」の特例も正確
- 制度調査は一次資料ベースでアナロジー採用理由が追跡可能
