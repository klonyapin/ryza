規程 `docs/design/08-meta-audit.md` と `ops/reminders.yaml` のエントリ `meta-audit-2026q4` は、A-12 F-11 の是正3点(①リマインダー登録 ②手順の docs/design 文書化 ③実施記録の証跡化)を骨格として満たし、独立性・入力の point-in-time 固定・二重証跡という制度設計上の中核要件は水準を超える。一方で **文書層の分類が事実誤り**(L4 と自己申告するが実際は L3)、**保護領域 protected_areas 未登録**、**規程自体の改訂手続が曖昧**、**次回リマインダーの自動再登録に技術的裏付けがない** の4点が、規程の骨抜き耐性(§1・§6 の趣旨)と機械可読契約を弱めている。approve に足るには重大所見1件と中所見3件の是正が要る、というのが結論である。

## 重大所見

### 重大-1: 文書層の分類が事実と矛盾する(L4 と申告するが実際は L3)

規程冒頭に「文書層は L4(`config/governance.yaml` document_layers)」と明記されているが、`config/governance.yaml` L47-L82 の document_layers 定義では:

- L3 の docs 節に `path: docs/design/*.md`(draft_by: cio, department_job / review_by: independent_officer / approve_by: representative_deemed)
- L4 の docs 節には `config/*.yaml`, `docs/tasks/*.md`, `src/**`, `migrations/*.sql`, `ops/**`(すなわち docs/design は含まれない)

`precedence: highest_layer_match_wins` に従えば **`docs/design/08-meta-audit.md` は L3** である(より高い層 L1・L2 の個別 path マッチは無い)。L3/L4 で承認手続・審査要否が変わる(L3: 独立役員審査+みなし承認48h / L4: 設計リード承認、ただし保護領域なら独立役員審査)ため、これは表示上のミスでなく **統治文書の自己分類ミス**である。規程本体が §6 で「本規程の改訂は document_layers の手続に従う」と書いているため、正しい層を明示しないと第1回メタ監査以降の改訂手続に解釈の余地が残る。

**是正**: L4 → L3 に訂正し、続けて「改訂は独立役員審査+みなし承認48h(定款第3条)」と手続を明記する。

## 中所見

### 中-1: 規程が protected_areas に未登録 — 自己言及性の抜け

規程 §6 は「本規程自体もメタ監査の評価対象」「規程が緩められて EQA が骨抜きになる経路もメタ監査が見るべき形骸化」と自認するが、`config/governance.yaml` の protected_areas に `docs/design/08-meta-audit.md` が **登録されていない**。docs/design 配下でも 06-constitution / 80-ips / 70-writing-standard / 81-fm-mandates / 05-governance は個別登録されている(governance.yaml L85-L151)。同格の統制文書として本規程も登録すべきである — さもなくば「メタ監査を骨抜きにする改訂」(頻度緩和・独立性要件の削除・verdict 判定基準の書換)を無審査で通せる二段手順が残り、A-18-1 の突合対象にもならない。

本規程が主張する制度の骨抜き耐性は、`protected_areas` への登録なしには成立しない — これは今回 PR の中核主張と直接矛盾するため中所見とする。

**是正**: `config/governance.yaml` protected_areas に以下を追記(area は新設 `meta_audit`、または既存 `governance_doc` に寄せる。後者が文書性の観点では自然):

```yaml
- path: docs/design/08-meta-audit.md
  area: governance_doc
```

同 PR 内で対応するのが望ましい(規程だけ制定して保護されない状態のマージは、上記の抜け穴を実際に一時的に開ける)。

### 中-2: ラベル `governance` が GitHub 上に存在しない

`gh label list` で確認したが、リポジトリの実在ラベルは bug/documentation/enhancement/... および design/impl/decision/user-action/digest/in-progress の10種で、**`governance` ラベルは実在しない**。既存の reminders.yaml でも `governance` は5エントリ(reminders-status-tamper-detection, boardroom-effectiveness, meta-audit-2026q4 本件含む)で使われており、これは本 PR 固有の問題ではなく既存の慣行に従った結果だが — 次に発火する governance 系リマインダー(boardroom-effectiveness は 2026-11-24)より前に meta-audit-2026q4 が発火する(2026-11-01 date_after)ため、**本エントリが「未存在ラベルでの issue_create に失敗する GitHub API 挙動」を実地で最初に踏む可能性が高い**。

GitHub の POST /issues API は存在しないラベルを含む payload に対して 422 を返す(サーバー実装により label auto-create も設定次第だが、既定は 422)。`src/ryza/ops/github.py:146-155` の `create_issue` は labels を素通しするため、422 で issue 作成そのものが失敗する。fired への更新は成功時ロジックだけであれば無限リトライまたは無サイレント失敗のリスクがある(weekly.py の失敗時挙動は未確認 — 追加検証を推奨)。

**是正候補**(いずれか):
- (a) GitHub 側に `governance` ラベルを事前作成する(`gh label create governance --description "統治・監査系" --color "..."`)。既存の governance 系4件が今後発火するため、いずれにせよ必要
- (b) labels を既存の `decision` に置換する(EQA 結果は経営会議の議題であり、意味的にも近い)

(a) を推奨。governance ラベルは既存慣行として存在しており、単に登録漏れ。本 PR は「使う側」なので、同 PR 内で `gh label create` を実行または task に登録するのが自然。

### 中-3: 「次回分を登録」の実行主体が未指定・技術裏付けなし

規程 §5-4 と reminders.yaml エントリ body の双方が「完了時は本エントリを fired に更新し、次回分(+3ヶ月)を登録すること」と書くが、この再登録を **誰が/どのジョブが行うか** の明示がない。他の recurring reminder(ips-quarterly-review・boardroom-effectiveness)も同じ書き方を採用しているため本エントリ固有の欠陥ではないが、`src/ryza/ops/weekly.py` を grep しても re-register 相当の実装は無く(next_id_re は YAML パース用の正規表現に過ぎない)、**再登録は暗黙に人間か会話中のエージェントに委ねられている** — CLAUDE.md「セッション内の約束は無効」の趣旨に反する構造である。

四半期に1度、issue が起票された後に誰かが「気付いて」YAML に次回エントリを足す運用は、フェイル・オープン(気付かなければ次回は永遠に来ない)である。EQA が骨抜きになる経路として本規程が §1 で列挙した「fired にならないまま放置」を、本規程の実行機構自身が **構造的に持ってしまっている**。

**是正候補**:
- (a) `ryza-weekly-check` 定例ルーチン(または後継の ops-weekly ジョブ)に「fired にした recurring reminder の次回エントリ自動生成」を実装する。今回 PR ではスコープ外だが、TODO として reminders.yaml に別エントリで登録する(自己参照的だが機械可読契約としては正しい)
- (b) 最低限、規程 §5-4 で「再登録は Claude 定例ルーチン(ryza-weekly-check)の責務」と実行主体を明示する。手続の帰属点を書けば、少なくとも監査(A-18)は放置を検出できる

### 中-4: verdict 二値の判定基準に運用可能な閾値が無い

規程 §5-1 は verdict を `effective | degraded` の二値と定めるが、**どのような所見が出たら degraded 側に振れるかの判定基準が §4 の評価軸(網羅性・実効性・形骸化)にも書かれていない**。例:

- 網羅性のゼロトレランス4領域(帳簿分離/ゲート迂回/保護領域/証憑)のうち1領域でも検査が無ければ即 degraded か、それとも「検出感度が下がっている」だけで effective 側か
- 「同型所見の再発」は何回で形骸化認定か
- 「懸念ゼロ報告の連続」は何回連続で degraded か(05-governance §6-5 は「連続」としか書いていない)

規程 §4 末尾は「あら探しの件数でなく監査が今も痛い指摘を出せるかの判定」と定性判定を宣言するが、これは実施者(別系統 AI)の裁量に判定を丸投げすることを意味する。プロンプト分離下で盲検された実施者が「痛い指摘を出せるか」の主観判定を出すのは、まさに **議論規約4「意見でなく証拠で解決」の反対** である。

判定の再現性(次回の別実施者が同じ入力に対して同じ verdict を出せるか)を担保しないと、規程は「実施者次第で結論が変わる評価」を制度化することになる。

**是正候補**: §4 に degraded 認定の最小基準を追加する。例:

- 「ゼロトレランス4領域のいずれかに自動検査の対応が無い」→ degraded 確定
- 「同型所見が2四半期連続で再発」→ degraded
- 「A-18 の全検査に3回連続で指摘ゼロ」→ 少なくとも「反対すべき点を探して見つからなかった」の明示的正当化が verdict 冒頭に必須(既に議論規約1で暗黙に要求されているが、規程で明文化する)

具体閾値は運用実績に応じ後日調整可能な旨も併記すればよい。第1回は試行と位置づける PR 反対意見書1の代替案とも整合する。

## 検出対象外のケース(残余リスク)

規程の形骸化耐性(検証観点5)について、以下は **本規程では検出できない**:

1. **実施者(別系統 AI)自体の劣化**: 別系統 AI が「痛い指摘を出せる能力」を失った場合(モデルが warning-averse になる・システムプロンプトが甘くなる)を、本規程の枠組みでは検出できない。年次のガバナンス実効性評価(00-system-design §6)で扱うべきだが、実効性評価もメタ監査の実施者に依存するため循環参照がある。反対意見書2の指摘とも重なる残余リスク
2. **裁定側の骨抜き**: 規程 §5-2「裁定は設計リードが行い、A-12 裁定書と同じ形式で残す」は、設計リードが所見を「取るに足らない」「実装コストが高すぎる」等で軒並み棄却する経路を塞いでいない。A-12 裁定は独立性が担保されていたが、四半期の EQA 裁定を設計リード単独に委ねるのは、裁定側の独立性設計として弱い(定款第3条の3専決には該当しないが、代表への通知やユーザー閲覧の仕組みが規程に無い)
3. **入力 §3 の意図的欠落**: 実施者が §3 の標準入力セットの一部を「調達できなかった」として省略する経路は、レポートに開示義務は無い。中-4 の verdict 判定基準の曖昧さと組み合わさると、実効的な骨抜き経路になる
4. **レポート未執筆で fired 遷移**: 規程 §5-4 は二重証跡(レポート+fired)で偽装耐性を主張するが、**「レポートを書かずに fired だけ更新する」経路** は自動検知されない。A-18 系がレポートファイルの存在検査を持たないため。PR 反対意見書3 の指摘と同じ

これらは規程 v1.0 のスコープ外として明示するか、次回改訂の宿題として reminders 登録するのが望ましい。

## verdict とその根拠

**verdict: request_changes**
