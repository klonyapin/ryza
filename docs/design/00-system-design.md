## 0. 基本構造(最重要)

**取引は二系統**: デモ取引系統(当面はこちらのみ。IBKR ペーパー/Saxo SIM/Testnet)と実取引系統(将来。立花 e支店/IBKR ライブ)。同一コードパス、アダプタと設定のみで分離。

**会計は二系統・帳簿3エンティティ(book_id で完全分離、混合はスキーマ制約で禁止)**:
1. デモファンド帳簿(架空)— 仮想資金の複式簿記
2. 実取引ファンド帳簿(将来)— 実弾開始時に新設、①から引き継がない
3. 運営会計帳簿(実費)— GCP・LLM API・データ費・手数料等、実際のお金

E4(全コスト込み評価)は、③の実費を戦略・部門別にタグ付け配賦し評価時に①と結合(デモ帳簿にみなし記帳はしない)。

## 1. 用語定義(評価プロトコル E1〜E7)

- **E1 カットオフ後評価**: LLM 関与戦略の過去検証は使用モデルの学習カットオフ後の期間のみ(期間内の好成績は記憶の再生。統制で最大 -71.85% の実証)
- **E2 前向き検証**: 採用の最終判断はペーパートレードの前向き検証
- **E3 ベースライン対照**: 等配分 buy-and-hold にコスト込みで勝てない戦略は不採用
- **E4 全コスト込み**: 手数料・スリッページ+LLM トークン費・データ費込みの純損益で評価(運営会計から配賦)
- **E5 分散の報告**: 複数シード実行でばらつきを報告。短期 Sharpe 差で意思決定しない
- **E6 point-in-time ユニバース**: その時点で選べた銘柄群で検証(生存者バイアス排除)
- **E7 単一エージェント対照**: マルチエージェント構成は単一構成との対照比較後に採用
- **E8 資本スケール&開始時点スイープ**(2026-08-02 追加): 全戦略評価は初期資本のグリッド(¥10万・30万・50万・80万・100万)×複数の開始時点(ローリング)で実行し、成績が特定の資本規模・開始タイミングに依存しないことを確認する。売買単位(日本株100株)・最低手数料・端数制約は資本規模ごとに現実どおり適用する(小資本では実行可能ユニバース自体が変わるため)。ペーパー運用でも資本規模の異なる仮想帳簿を並走させてよい
  - 方法論上の位置づけ: 開始時点スイープはウォークフォワード/サブサンプル頑健性検証として主流(Pardo; White 2000 Reality Check; Hansen 2005 SPA)。資本グリッドは教科書的手法ではないが、キャパシティ分析の小口側ミラーとして単元制約の現実モデリング(標準原則)から必然的に導かれる
- **E9 多重検定補正**(2026-08-02 追加): ストラテジー動物園で試行した全戦略・全パラメータの試行数を記録し、採用判定には多重検定を補正した指標 — **Deflated Sharpe Ratio(Bailey & López de Prado 2014)および バックテスト過剰適合確率 PBO(Bailey et al. 2014, CSCV 法)** — を用いる。「多数試せば偶然勝つものが出る」問題への標準的対処であり、生の Sharpe による採用判定を禁止する。試行数の記録は隠れた多重性(却下した実験も含む)を含めること

その他: as_of(情報が利用可能になった時点)/ NAV / TWR / VaR・ES / ウォークフォワード / IPS(投資方針書=憲法、人間のみ起票可)/ HITL / 証憑 / ブレイク / シャドー会計 / TCA — 詳細は Artifact §02。

## 2. 設計原則(v1 から継続)

1. LLM は判断材料を作る側。お金を動かす経路(シグナル合成→サイジング→ゲート→執行→会計)は決定論
2. コンプライアンスゲートが唯一の発注経路
3. 全データ as_of 付き不変保存、分析は point-in-time
4. 判断来歴の全保存
5. モジュール間はデータ契約のみで疎結合
6. 最小構成+移行路の確保

## 4. ファンド会計部(強化)

- **証憑必須**: 全仕訳行に evidence_id NOT NULL。証憑(約定 API レスポンス原文+ハッシュ、価格スナップショット参照、GCP Billing Export 行、請求書)は証憑ストアに不変保存
- **財務諸表の常時閲覧**: 試算表(日次)、BS(日次/月次)、PL(月次/累計)、CF(月次)、運用報告書(月次)を帳簿エンティティ別に自動生成、ダッシュボード常設+月次 Discord 配信
- 記帳原則: 約定日ベース、実現/未実現分離、発生主義、日次締め→照合→一致で NAV 確定/不一致でブレイク管理

## 6. 独立監査部門(新設)

独立性: 別実行環境(別 Cloud Run ジョブ・別サービスアカウント)、read-only 権限、投資委員会直属報告、本体と別系統のモデル/プロンプト。監査部門のコードは保護領域(R&D の PR 対象外)。

監査項目: A-1 仕訳と証憑の突合 / A-2 照合状況とブレイク滞留 / A-3 ゲート迂回検知(executions×ゲートログ突合)/ A-4 リスクリミット遵守 / A-5 承認ログ完全性 / A-6 E1〜E7 遵守 / A-7 帳簿分離の維持 / A-8 予算執行の妥当性 / A-9 保護領域の変更管理 / A-10 as_of 整合(point-in-time 違反検知)。A-1〜A-5 は実弾移行の前提条件。

### 実装監査(コード監査)— 2026-08-02 追加(ユーザー指示)

システムは自己改変を続けるため、**プログラム・仕様のバグを発見する実装監査は恒久機能**とする。担い手は実装・承認に関与しない**別系統の AI(実装が Claude 系のため、監査は別ベンダーのモデルを推奨。構成可能)**。

- **A-11 PR 監査(変更駆動)**: 自己改変ループの全 PR に、独立系統 AI のコードレビュー意見(バグ・仕様乖離・保護領域への影響)が添付されてからでないと委員会承認に進めない
- **A-12 定期コード監査(四半期)**: 設計文書と実装の突合(仕様乖離の検出)、テストの穴(境界値・異常系・E プロトコルの検証漏れ)、依存関係の健全性を監査し、指摘事項トラッカーに登録
- 第1回のフル実装監査は「最初の運用可能版(データ取込→分析→朝刊が動く時点)」で実施

### 運用カレンダー「営業期間=1ヶ月」と柔軟な監査(2026-08-02 ユーザー指示)

実会社の年次カレンダーに縛られない。**営業期間=1ヶ月**とし、レビュー類を2分類で圧縮する:

- **労働律速(AI 労働のみで完結)→ 大幅圧縮**: 月次決算=本決算扱い / IPS レビュー 四半期→**月次** / A-12 コード監査 →**月次** / A-16 リストア検証 →**月次(自動)** / メタ監査・ガバナンス実効性評価 年次→**四半期**(月次化は12倍のコストで検出価値が見合わない — 設計リード対案)
- **データ律速(取引・成績データの蓄積が必要)→ カレンダーでなく最小サンプル基準で駆動**: 遵守統計・実現率・Brinson・意見反転統計は「n≥基準(例: 20営業日分)」を満たしたときに評価。未達のままレビュー日が来た場合は「データ不足」と明記し無理に判定しない(統計的に無意味な高頻度化の防止)

**重要性基準(materiality)とリスクベース監査**: 実務の監査同様「あえて深追いしない」を制度化する:
- **軽微基準**: NAV の 0.1% 未満のブレイク・差異は個別追跡せず集計のみ(月次で件数・合計を報告)。閾値超のみ個別追及
- **リスクベース配分**: 全件自動チェック(安価)は維持しつつ、人手・LLM の深掘りは「事故履歴・変更頻度・金額規模」でリスクスコア上位に集中。監査資源は固定予算内で再配分
- **ゼロトレランス領域(金額不問・絶対に見逃さない)**: 帳簿分離違反 / ゲート迂回 / 保護領域の無承認変更 / 証憑の欠損・改竄。実務でも不正の兆候に重要性基準は適用しない — ここだけは柔軟にしない

### 監査部門自体の更新機構(メタ監査)— 2026-08-02 追加

監査部門のコードは保護領域(R&D の自動 PR 対象外)のため、更新は以下の専用経路で行う:

1. **事故駆動の追加(常時)**: 監査をすり抜けた事故・バグは必ずポストモーテムを書き、「どの監査項目があれば検出できたか」を特定して監査項目を追加する。事故→監査強化のループを義務化
2. **年次メタ監査**: 年1回、**さらに別系統の AI** が「監査部門の監査」を実施 — 監査手続きの網羅性・実効性・形骸化(指摘の質の劣化)を評価する。IIA 実務の外部品質評価(EQA)の移植
3. **監査 KPI の常時計測**: 指摘の検出→解消リードタイム、再発率、監査発の重要発見数を経営会議で報告(監査が働いているかを数字で見る)
4. **変更の実行**: 監査コードの変更はユーザー起票+実装後、通常と逆向きのレビュー(実装系 AI がレビュー)+二重確認で適用。監査計画(項目・頻度)の改訂は年次のガバナンス実効性評価で決議

- **文体規定**: センテンス抽象度5段階(1=純粋なファクト、2=観察、3=概念的まとめ、4=方向付け、5=アブストラクト・アーギュメント)。パラグラフは 4→3→2→1→3→5 の U字が理想形。執筆エージェントが文ごとに抽象度タグを出力し、決定論的リンターが U字形状と「レベル1の文の出典紐付け」を検査、不合格は再生成
- **embed 仕様**: リッチ embed+**アニメの女の子の画像**(生成 or ライセンスクリアな自前アセットのローテーション)。速報は embed 色を赤に
- **速報**: ①緊急ニュース(即時)②報道前の予兆(複数の弱いシグナルの同方向一致。確度・根拠明記で事実と区別、事後検証で予兆精度を評価)。監視は GCE 常駐+場中定期ジョブ(階層0の異常検知→軽量→中位のエスカレーション)
- **表現ルール(v3.1)**: 完全非公開サーバーのため**個別銘柄の売買推奨表現は許可**。コンプライアンス部のチェックは「非公開設定の維持」と「推奨の根拠(出典)の存在」に変更。公開範囲拡大時のみ制限復活フラグ

## 8. 研究本部(3班+モデル階層)

- **戦略研究班**: Fable が仮説生成・研究設計 → E1〜E9 バックテスト → 論文形式で蓄積(プレプリント級品質目標)。有望なら戦略部門へ採用申請。**ノルマ(2026-08-02 改訂)**: 週5本を上限とし、E9 を通る仮説が無い日は「負の結果レポート」でよい(負の結果も同一クレジット — 量が質を駆逐する日次ノルマの弊害と p-hacking 誘因を防ぐ)

### 研究制度 v2(2026-08-02 全面改訂 — 根拠: docs/research/research-methodology.md)

v1 は事前登録を研究全体の核に置いたが、これは「探索(仮説がまだ無い段階)を制度から締め出す」欠陥があった(ユーザー指摘・調査で裏付け)。v2 の設計:

**1. 二つのモード(混同のみを禁じる)**
- **探索モード**: 自由。仮説不要・データいじり歓迎・何でも試してよい。禁止事項はただ一つ、探索の結果を統計的証拠として主張すること。産物は「観察ノート+メカニズム仮説(アブダクション: この異常を最も良く説明する経済的機構は何か)」
- **確証モード**(昇格ゲートでのみ): テスト仕様(データ範囲・ホールドアウト・成功基準)を事前固定してから実行。事前登録はここに限定。逸脱は禁止でなく「申告+検定の厳しさへの影響評価」で扱う(Lakens/Rubin)

**2. 実験台帳(事前登録より強い基盤)**: 全バックテスト・全試行はシステムが自動記録する(リネージ基盤で実装済みの前提)。人間の科学が事前登録で代替している「試行回数の可視化」を実測し、E9 の DSR/PBO は台帳の N で計算する。探索の自由を一切奪わずに多重性を正確に補正できる — AI 研究組織の構造的優位

**3. 評価単位は研究プログラム(Lakatos)**: FM・研究テーマは「堅い核(経済メカニズム仮説)+防護帯(実装・パラメータ)」を明示し、個別の検定結果でなく**軌跡**(新奇な予測を当て続けているか/後付け修正ばかりか)で継続・打ち切りを判定。単発の失敗では殺さず、退行の持続でのみ殺す

**4. 開発と検証の分離(生産チェーン)**: シグナル開発者(FM/研究班)と検証者(バックテスト・昇格判定)は別エージェント。検証エージェントの評価関数は昇格数でなく「偽陽性の検出」(López de Prado の分業論)

**5. 昇格ゲート(探索→本番の移行段階を明示)**: 探索 → 予備検証(IC 安定性等)→ 確証(事前固定プロトコル+ホールドアウト+多市場 OOS、閾値は多重検定調整済み t>3 相当)→ ペーパー小配分 → 劣化監視。各段で要求証拠水準を上げる

**6. プログラム開始時は Heilmeier 問答**: 何をするか(専門用語なし)/現状の限界/新規性/成功したら何が変わるか/リスク/**中間・最終試験は何か**。分析手順でなく成功基準だけを固定するので探索を殺さない(DARPA)。プログラムには固定期限と損切り・再配分ルールを付す

**7. 負の結果の登録義務(Registered Reports 型)**: 確証モードに入った検証は結果に関係なく台帳に正式記録。負の結果も研究クレジットとして同等に計上(file drawer 問題の防止、DSR の前提)

**8. 評価指標(改訂)**: プロセス層(週次・自動): 執筆規格・実験台帳の完全性・モード混同ゼロ — **数値目標はここだけ** / ファネル層(月次): 各段通過数・負の結果数 / 実現層(データ律速): 昇格戦略のライブ÷バックテスト実現率 / 品質層(月次・盲検): 別系統 AI の採点。Goodhart 対策(昇格数を目標化しない)は継続

**9. メタ制度**: 閾値・昇格基準などの規律ルール自体が長期の発見効率に与える影響を、システム研究班がシミュレーションで定期検証し改訂提案する(Devezer らの形式的方法論)
- **執筆規格(v3.2)**: 価値あるすべての文章は `docs/design/70-writing-standard.md`(保護領域)に従う — 3部構成、モデル論文計測による型習得、Uneven U(4→3→2→1→3→5)、引用の数値管理と必須文献(モデル論文2本共通引用)、イントロの順番(冒頭→先行研究→アーギュメント複数回パラフレーズ→シノプシス)、結論の型(応用可能性+4類型)。リンターで機械検査
- **情報分析班**: ニュース・決算公告・中銀/政府発表・政策・法案・裁判・社会情勢・Reddit・5ch(旧2ch)等の分析研究。シグナル候補とテーマレポートを供給
- **システム研究班**: データ基盤の研究(収集対象・スキーマ)+組織構造自体の研究(部門編成・エージェント構成・承認フロー)
- **モデル階層ポリシー(v3.1 改訂)**: **階層0=非LLM**(ルール・正規表現・古典ML: ロジスティック回帰/勾配ブースティング/fastText の分類、埋め込み+近傍法の重複排除、統計的異常検知)を最優先し、済むなら LLM を使わない/軽量 LLM=非LLMで精度が出ない処理のみ/中位(Opus・zlm 級)=日常分析・実装・執筆/Fable=研究設計・仮説生成・論文執筆・重要レビュー(週次少量)。エスカレーション規則付き。消費は経営管理部が予算管理
- **自己改変ループ**: 提案は PR → 自動検証 → Discord 承認 → Cloud Build デプロイ。保護領域(ゲート・リミット・Kill Switch・会計・監査)は二重確認、IPS は人間のみ

### マルチマネージャー制(ポッド制)— 2026-08-02 追加(ユーザー指示)

実在のマルチマネージャー・プラットフォーム(ポッド型ヘッジファンド)を移植し、戦略部門・PM 部を「複数のファンドマネージャー(FM)ペルソナ」に再編する:

- **FM = 人格化された役職資産**(05-governance.md の仕組みを使用): 各 FM は名前・運用哲学・永続記憶(自分の判断履歴と反省)・モデル指定を持ち、固有のマンデート(戦術範囲・ユニバース・IPS プロファイル)と仮想資本の配分を受ける
- **中央機能は唯一のまま(プラットフォームの鉄則)**: リスク管理・コンプライアンス・会計・執行・監査は全 FM 共有。FM はシグナル/注文案を出すだけで、発注経路・リスク上限の変更権を持たない
- **人事制度 = ライフサイクル**: 採用(孵化: 事前登録済み仮説+E1〜E9 通過)→ 仮想資本の初期配分 → 評価(実現率・DSR、帰属明確)→ 増額/減額(月次再配分)→ 解任(退役。記憶は保存し、事後分析の資料に)
- **FM 数に固定上限なし**: 制約は ①経営管理部の月次 LLM 予算 ②E9 多重検定補正(FM が増えるほど「偶然の勝者」判定が厳しくなる自動ペナルティ)③データ蓄積速度。予算内・補正後有意なら何人でも
- **中央リスクの追加責務**: FM 間の相関監視(全員が同じベットに乗る「隠れ集中」の検出 — FF 回帰のポッド横断版)。プラットフォーム型の主リスクはここにある

```mermaid
flowchart LR
  subgraph VM["GCE e2-micro us-west1 — 無料枠"]
    BOT["Discord Bot 常駐"]

  end
  subgraph RUN["Cloud Run — 無料枠内"]

  SCH["Cloud Scheduler"] --> JOBS

  EXT["デモ取引 API"] <--> JOBS
  CB["Cloud Build(承認済み PR)"] -.-> RUN
  CB -.-> VM
```

GCE e2-micro 無料枠(Bot+PostgreSQL+pg_partman+pgvector 同居)+ Cloud Run Jobs/Scheduler + Streamlit(min=0)= 月額 $0〜数ドル。v3 追加: Billing Export(BigQuery)有効化(実費記帳の一次証憑)、監査用の別サービスアカウント(read-only)、証憑ストア(Cloud Storage、ハッシュ改竄検知)。

v3.1 追加:
- **データリネージ**: 全取込データ・生成物(レポート・シグナル・注文・記事)に「生成ジョブ・コードバージョン・入力データ参照・as_of」を記録。任意の成果物から原データまで遡れるリネージグラフを維持(判断来歴はこの上に載る)
- **データカタログ**: 全テーブル・データセットの説明・スキーマ・鮮度をダッシュボードに常設
- **ベクトル検索**: テキスト系の埋め込みは pgvector(Postgres 内のベクトルDB)。数百万件超で Qdrant 等への移行路
- **常時稼働**: GCE 常駐プロセス(取込・監視・市場観更新・Bot)+イベント駆動 Cloud Run ジョブ。随時稼働の主体は階層0(非LLM)なのでコスト増なし
