Ryza は自己のコードを自己改変する組織であるため、開発部門は他のどの部門よりも先に統治される必要がある。本書は開発部門を正式に設置し、変更管理・品質保証のプロセスを執行点付きで定める(執行点のない条項は置かない — 定款第6条)。

## 1. 開発部門の設置

- **責務**: Ryza 本体の設計・実装・品質保証・デプロイ。00-system-design の部門表に「開発部門」を追加する(成果物: 設計文書・実装指示書・PR・リリース。サイクル: 常時)
- **構成**: 設計リード(Fable 級 — 設計・実装指示書・レビュー・統合の権限を持つ)+実装エージェント(中位モデル — worktree 内での実装・テストのみ。main への統合権限を持たない)+独立役員(保護領域・重要変更の審査 — 開発部門の外部)
- **権限・義務・禁止**(定款第7条の3分類。charter: `personas/dev-lead/charter.md`):
  - 権限: 非保護領域の変更の起票・統合(PR 経由)。保護領域は起票のみ(承認は定款第3条)
  - 義務: 本規程のプロセス遵守、審査意見書の保存(docs/reviews)、指摘メトリクスの記録
  - 禁止: PR を経ない main への変更(ブランチ保護+A-13-4)、自己の権限の自己拡大、承認記録の偽装

## 2. 変更管理(ISO 9001 8.5.6・8.3.4 の借用)

1. **全変更 PR 化**: リポジトリへの全変更は PR 経由とする。例外なし。執行点: ブランチ保護(PR 必須・CI 必須・force push 禁止・管理者含む)+A-13-4(直 push 検出の二重底)
2. **記録の定義**(監査証拠性の前提 — 実務調査 §2): 本規程により次を正式記録と定義する: **PR 説明文=変更依頼と影響評価/PR マージ=変更の許可(許可者=マージ実行者)/PR タイムライン+コミット履歴=監査証跡**。保護領域はさらに `Approved:` トレーラまたは PR 手続で承認記録と突合(定款第5条)
3. **三分割**(8.3.4): **レビュー**=設計リードのコードレビュー+保護領域・重要変更の独立役員審査(意見書は docs/reviews に保存)/**検証**=CI(全テスト・lint・YAML 検証。required check)/**妥当性確認**=統合後のデプロイ実走スモーク(daily/bot/監査ジョブの実環境一巡確認)。検証と妥当性確認を混同しない(CI 通過はリリース妥当性を意味しない)
4. **実装指示書**(29110 Basic の PM/SI テーラリング): 設計リードは自己完結の実装指示書(docs/tasks/T-0xx)を起票してから委譲する。指示書=作業範囲記述+計画、受け入れ基準=合否判定基準(8.3.5)、エージェント報告=進捗記録。軽微な変更(指示書を要しない規模)は PR 説明文がこれを代替する

## 3. 品質保証(SQuBOK 技法の選定)

1. **AI 実装のインスペクション**: 保護領域・新規モジュールの実装は、実装エージェントと**独立の審査エージェント**(プロンプト分離・批判専任)によるインスペクション相当の審査を必須とする。攻撃シナリオの構築・実証を審査観点に含める(本日の実績: T-014 で2バイパス実証→是正)
2. **テスト**: 仕様ベース(境界値・状態遷移)を基本とし、発効 config の実値を直接検証するリグレッションテスト(保護領域の値固定)を必須とする。テストは CI で全件実行
3. **メトリクス**: 独立審査の指摘件数・重大度・是正率を docs/reviews の意見書から集計可能な形式で蓄積する(IPA 目安値は母集団が異なるため参考に留め、自前ベースラインを構築 — 執行点: 監査部門の四半期棚卸しで傾向を報告)
4. **是正処置**(10.2): 障害・監査指摘は Issue で管理し、封じ込め→原因分析→**水平展開**(同種の欠陥が他所にないかの探索)→是正→**有効性レビュー**(再発がないか)の型で扱う。重大障害は docs/reviews にポストモーテムを残す

## 4. AI 固有統制(ISO/IEC 42001・5338 の借用)

1. **エージェントログ**(42001 A.6.2.8): 実装エージェントの成果は worktree ブランチ+報告として記録され、審査・是正の往復も意見書に残す(本規程 §3-1)
2. **人間の監督**(A.9.2 相当): 代表はブランチ保護の管理者権限と定款第3条の専決・否認権を通じて監督する。エージェントは自らブランチ保護・リポジトリ設定を変更してはならない(執行点: GitHub 設定変更は代表の権限。A-13 の宣言棚卸し対象)
3. **継続的検証**(5338): デプロイ後の稼働は daily 実走・A-13 週次・freshness 監視が継続検証する。稼働コード=承認済みコードの突合(deploy SHA)は既登録の宣言統制(実弾移行前提)

## 5. 執行点対応表(定款第6条)

| 条項 | 執行点 | 種別 |
|---|---|---|
| §2-1 全変更 PR 化 | ブランチ保護(予防)+A-13-4(発見) | 予防+発見 |
| §2-2 記録の定義 | 本規程の明文+A-13-1 突合 | 宣言→監査 |
| §2-3 検証 | CI required check | 予防 |
| §2-3 妥当性確認 | デプロイ実走スモーク(手順) | 宣言(実走ログが証跡) |
| §3-1 独立審査 | 審査なし統合を A-13 拡張で検出(要実装 — 宣言) | 宣言 |
| §3-4 是正処置 | Issue テンプレート(要作成 — 宣言) | 宣言 |
| §4-2 設定変更の禁止 | GitHub 権限+宣言棚卸し | 予防+宣言 |

宣言マークの条項は四半期棚卸し(reminders 登録済み)で執行点昇格を再評価する。
