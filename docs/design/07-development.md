# 開発部門・開発管理規程 v0.1 ドラフト

- 作成: 2026-08-03 / ステータス: **ドラフト(独立役員審査 → みなし承認手続待ち)** / 層: L3(定款第4条)
- 上位文書: [06-constitution.md](06-constitution.md)(定款)、00-system-design.md / 根拠調査: [dev-quality-references.md](../research/dev-quality-references.md)
- 経緯: 2026-08-03 代表指示「全変更 PR 化・ISO 参考(+SQuBOK)・開発部門の設置」

Ryza は自己のコードを自己改変する組織であるため、開発部門は他のどの部門よりも先に統治される必要がある。本書は開発部門を正式に設置し、変更管理・品質保証のプロセスを執行点付きで定める(執行点のない条項は置かない — 定款第6条)。

## 1. 開発部門の設置

- **責務**: Ryza 本体の設計・実装・品質保証・デプロイ。00-system-design の部門表に「開発部門」を追加する(成果物: 設計文書・実装指示書・PR・リリース。サイクル: 常時)
- **構成**: 設計リード(Fable 級 — 設計・実装指示書・レビュー・統合の権限を持つ)+実装エージェント(中位モデル — worktree 内での実装・テストのみ。main への統合権限を持たない)+独立役員(保護領域・重要変更の審査 — 開発部門の外部)
- **権限・義務・禁止**(定款第7条の3分類。charter: `personas/dev-lead/charter.md`):
  - 権限: 非保護領域の変更の起票・統合(PR 経由)。保護領域は起票のみ(承認は定款第3条)
  - 義務: 本規程のプロセス遵守、審査意見書の保存(docs/reviews)、指摘メトリクスの記録
  - 禁止: PR を経ない main への変更(ブランチ保護+A-18-4)、自己の権限の自己拡大、承認記録の偽装

## 2. 変更管理(ISO 9001 8.5.6・8.3.4 の借用)

1. **全変更 PR 化**: リポジトリへの全変更は PR 経由とする。例外なし。執行点: ブランチ保護(PR 必須・CI 必須・force push 禁止・管理者含む)+A-18-4(直 push・非 PR マージ検出の二重底。実装: `src/ryza/audit/a18.py`・PR #47 で統合済み。**governance.yaml 統制テーブルへの登録は L1 PR 起票待ち** — 登録完了までこの発見統制は「登録待ち」状態)
2. **記録の定義**(監査証拠性の前提 — 実務調査 §2): 本規程により次を正式記録と定義する: **PR 説明文=変更依頼と影響評価/PR マージ=変更の許可(許可者=マージ実行者)/PR タイムライン+コミット履歴=監査証跡**。保護領域はさらに `Approved:` トレーラまたは PR 手続で承認記録と突合(定款第5条)
3. **三分割**(8.3.4): **レビュー**=設計リードのコードレビュー+保護領域・重要変更の独立役員審査(意見書は docs/reviews に保存)/**検証**=CI(全テスト・lint・YAML 検証。required check)/**妥当性確認**=統合後のデプロイ実走スモーク(daily/bot/監査ジョブの実環境一巡確認)。検証と妥当性確認を混同しない(CI 通過はリリース妥当性を意味しない)
4. **実装指示書**(29110 Basic の PM/SI テーラリング): 設計リードは自己完結の実装指示書(docs/tasks/T-0xx)を起票してから委譲する。指示書=作業範囲記述+計画、受け入れ基準=合否判定基準(8.3.5)、エージェント報告=進捗記録。軽微な変更(指示書を要しない規模)は PR 説明文がこれを代替する

## 3. 品質保証(SQuBOK 技法の選定)

1. **AI 実装のインスペクション**: 保護領域・新規モジュールの実装は、実装エージェントと**独立の審査エージェント**(プロンプト分離・批判専任)によるインスペクション相当の審査を必須とし、意見書を docs/reviews に保存する。攻撃シナリオの構築・実証を審査観点に含める(実績: [A-13 審査(現 A-18)での2バイパス実証](../reviews/a13-audit-independent-review.md)、[T-014 審査と是正](../reviews/t014-design-decisions.md))

   **意見書の様式(新様式 v1・2026-08-04 追加)**: 意見書は先頭に YAML front matter を持つ。審査対象コミットを**審査側が**機械可読に記録することが目的であり、これが無い限り承認記録の `reviewed_sha` は起票者の申告のままだからである(出典: [g-a18-protect 審査](../reviews/g-a18-protect-independent-review.md) 重要-3、`ops/reminders.yaml` `reviewed-sha-from-review-agent`)。

   ```yaml
   ---
   reviewed_sha: 0123456789abcdef0123456789abcdef01234567   # 審査対象コミットの完全 SHA(40 桁 hex)
   review_date: 2026-08-04                                   # 審査日(ISO)
   verdict: conditional_approve                              # approve | conditional_approve | reject
   ---
   ```

   - **実装**: パーサは `src/ryza/reviews.py`。`reviewed_sha` は 40 桁 hex の完全 SHA のみ(短縮 SHA は突合を「一致とも不一致とも言えない」状態にする)。`verdict` の語彙外・`review_date` の様式不備は警告にとどめ、発効は止めない(判定名の揺れで発効が止まると様式そのものが忌避される)
   - **執行点**: `python -m ryza.governance.decisions --deemed / --deemed-for-pr` は、`--review` がリポジトリ内の新様式意見書を指す場合に `reviewed_sha` を**審査側の記録から採用**し、起票者の `--reviewed-sha` と食い違えば**発効を中止する**(fail-safe)。**verdict が `reject` / `request_changes` の意見書を `--review` に指した場合も発効を中止する**(2026-08-04 独立役員審査 C-1・fail-safe 全面化 — 「意見書に不承認が書いてあるのに CLI が通す」経路を塞ぐ)。PR の head SHA との相違は中止せず注記のみとする —— 意見書のコミット自身が head を進めるため、審査対象 SHA と head は通常一致しない。`--kind pr` の実行では **`--review` の実在も検査し、参照先が読めなければ発効を中止**する(`--review-missing-ok` を明示すれば警告扱いに落とせる — 移行期の旧様式向け救済フラグ・C-2(c))
   - **後方互換**: front matter を持たない既存の意見書は**旧様式**として扱い、遡及改変しない(過去の審査に後から front matter を足せると「審査側の記録」が起票者の申告と区別できなくなる)。旧様式では従来どおり起票者の申告・PR head SHA が入る
   - **監査**: A-18-8 が、突合できた `reviewed_sha` のうち審査記録に由来する件数(`from_review_artifact`)を毎週開示する。由来のない一致は「起票者が両側に同じ値を書いた」ことしか意味しない。**由来なしの件数はカテゴリ別に内訳を出す**(旧様式・新様式で SHA 欠落・意見書が別の SHA を宣言・参照が読めない・**事後製造の疑い**(意見書 commit が決定より後)— 2026-08-04 C-3/C-4)。事後製造の判定は `git log --follow` で意見書の**初出コミット時刻**を取り、承認記録の `decided_at` と比較する(監査時点の作業ツリーだけを見て決定より後に足された意見書を由来に数えていた旧実装を是正)
   - **参照の解決**(C-2 是正・2026-08-04): `--review` に渡す参照は次の書式に**正規化**して読む —— (a) `..` を含むリポジトリ相対パスは正規化してリポジトリ内に落ちるものだけを受理し、外に出るものはエラーで中止する(旧実装の「`..` を含む参照はリポジトリ内でない」判定は無音の迂回口だった)、(b) **自リポジトリの GitHub blob URL** (`https://github.com/<owner>/<repo>/blob/<ref>/<path>`) はリポジトリ相対パスに変換して読む(他リポジトリの blob URL は従来どおりリポジトリ外扱い)、(c) 絶対パス・symlink 経由でリポジトリ外を指す参照はエラーで中止、(d) front matter の**先頭の空行**を許容する(0 行目のみを開始フェンスと見なしていた旧実装は、空行 1 行入れるだけで front matter を無効化できた)、(e) front matter のトップレベルキー重複は拒否する(`yaml.safe_load` の後勝ちで採用値が無警告に入れ替わる経路を塞ぐ)
   - **残る限界**: 意見書はリポジトリ内の平文であり審査エージェントの署名は無い。起票者が front matter を書き換える・front matter を消して旧様式に「戻す」経路は残る(署名 = 審査エージェントの鍵は将来課題)。監査側の C-3 判定は決定と意見書 commit の時系列で決まるため、**意見書と決定を同一 commit に含める(または decided_at 直前に commit する)ことで擬似的に「決定より前」に見せる**経路は完全には塞げない(サブ秒の粒度で見るには commit signing の署名時刻が要る)
2. **テスト**: 仕様ベース(境界値・状態遷移)を基本とし、発効 config の実値を直接検証するリグレッションテスト(保護領域の値固定)を必須とする。テストは CI で全件実行
3. **メトリクス**: 独立審査の指摘件数・重大度・是正率を docs/reviews の意見書から集計可能な形式で蓄積する(IPA 目安値は母集団が異なるため参考に留め、自前ベースラインを構築 — 執行点: 監査部門の四半期棚卸しで傾向を報告)
4. **是正処置**(10.2): 障害・監査指摘は Issue で管理し、封じ込め→原因分析→**水平展開**(同種の欠陥が他所にないかの探索)→是正→**有効性レビュー**(再発がないか)の型で扱う。重大障害は docs/reviews にポストモーテムを残す

## 4. AI 固有統制(ISO/IEC 42001・5338 の借用)

1. **エージェントログ**(42001 A.6.2.8): 実装エージェントの成果は worktree ブランチ+報告として記録され、審査・是正の往復も意見書に残す(本規程 §3-1)
2. **人間の監督**(A.9.2 相当): 代表はブランチ保護の管理者権限と定款第3条の専決・否認権を通じて監督する。エージェントは自らブランチ保護・リポジトリ設定を変更してはならない(執行点: GitHub 設定変更は代表の権限。A-18 の宣言棚卸し対象)
3. **継続的検証**(5338): デプロイ後の稼働は daily 実走・A-18 週次・freshness 監視が継続検証する。稼働コード=承認済みコードの突合(deploy SHA)は既登録の宣言統制(実弾移行前提)
