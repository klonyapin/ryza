- 出典となる審査: `docs/reviews/risk-navflow-rollforward-independent-review.md` 残渣修正審査記録 新-14 / 新-15 / 新-17

## 1. イントロ

### アーギュメント

評価替えを `securities` から独立勘定 `securities_mtm` へ分離すべき理由は「攻撃を塞ぐこと」ではなく、**取得原価と評価調整という別種の量を同じ勘定に足し込むのをやめれば、`securities = 約定再生の取得原価` という恒等式が毎日の締めで機械検査できるようになる**ことである。

### 本書の価値

本書は分離案の**利得と移行コストを実測で比較**し、採否を決める。同時に、この分離が **新-14 の攻撃を塞がない**ことを明示する — 塞ぐと誤解したまま `posted_by` 述語を外すと防御が純減するため、この点は採否そのものより重要である。

### シノプシス

§2 で分離案の中身、§3 で利得、§4 で移行コスト(実測)、§5 で採否と反対意見書、§6 で実装範囲、§7 で残る限界と申し送りを書く。

## 2. 何を変えるのか

### 2.1 現状

`securities` 勘定には性質の異なる 2 つの量が同居している。約定が積む**取得原価**(`post_fill`)と、締めが積む**評価調整**(`post_mark_to_market` の delta 累計 = 時価 − 取得原価)である。全売却後も残る「残渣」は後者だけなので、締めはそれを `_util.mtm_book_value` で**推定**していた — 判定子は `evidence.kind = 'price_snapshot'` と `journal_entries.posted_by ∈ MTM_POSTED_BY` の連言であり、どちらも仕訳の自由記入列である(`src/ryza/ledger/_util.py:329-394`)。

### 2.2 変更後

| | 変更前 | 変更後 |
|---|---|---|
| 取得原価 | `securities`(評価調整と混在) | `securities`(**原価のみ**) |
| 評価調整 | `securities`(混在) | `securities_mtm`(資産・評価調整勘定) |
| 残渣の同定 | 述語による推定 | `securities_mtm` の**残高そのもの** |
| BS 表示 | 有価証券(時価) | 有価証券(原価)+ 有価証券評価調整 |
| NAV | 資産 − 負債 | 同左(両勘定とも asset なので値は不変) |

`_util.securities_book_value`(帳簿価額 = 時価)の**意味と呼び出し側は変えない** — 中身を「2 勘定の合計」にするだけである。したがって `recon` の評価額突合、`statements` の BS/PL/CF、`risk` 側の NAV 読み取りは無変更で通る。

## 3. 利得

### 3.1 推定の除去(reminder が挙げていた利得)

`mtm_book_value` は述語つきの集計から**勘定残高**になる。逆仕訳の除外(`NOT EXISTS` の相関サブクエリ)も不要になる — 逆仕訳は貸方に同額を立てるので残高が自然に相殺するからである。関数本体は 23 行から 8 行に減り、判定子は消える。

### 3.2 検査可能な恒等式(本命)

分離の本当の価値は、**別々の量を別々の勘定に置いたことで両者を独立に突合できるようになる**ことである。分離後は次の 2 つが毎日の締めで成立すべき恒等式になる:

- **原価恒等式**: 各銘柄について `securities 残高(as_of) = replay_position の取得原価(as_of)`
- **残渣恒等式**: 数量ゼロの銘柄について、洗い替え後の `securities + securities_mtm = 0`

分離前は前者を書けない。`securities` が原価 + 評価調整なので、突合するには評価調整ぶんを**推定で差し引く**必要があり、推定子が汚染されていれば恒等式も一緒に汚染される(新-14 の実測がまさにその形である)。分離後の原価恒等式は評価替えの経路を一切参照しないため、片方の帳簿だけを動かした逆仕訳のオペミス(新-15 の実測ケース)を評価替えの経路と独立に名指しできる。

**恒等式が覆う範囲は原価勘定側だけである(重要 — 独立審査 新-19)。** 評価調整勘定を直接叩く偽装(締めジョブ名を騙った `Dr securities_mtm / Cr capital`)は恒等式に一切現れない(審査実測: NAV 13,000,000→10,000,000、`unexplained_residue` は空)。その経路の防御は §5.2-1 のとおり `posted_by` 検証と DB トリガであって、恒等式ではない。また恒等式は「同じ呼び出しが書いた 2 つの成果物の内部整合」であって実在性の検査でもない(§7・新-21)。本節の主張は「新-15 の検出漏れを塞ぐ」までであり、「新-14 を塞ぐ」ではない。

### 3.3 会計表示としての正しさ

原価と評価調整を分けるのは有価証券会計の標準的な表示であり、監査上も「取得原価がいくらか」を台帳から直接読めることに意味がある。現状は取得原価を知るのに約定再生(コード)を通す必要がある。

### 4.1 データ移行

**ゼロである。** 2026-08-04 時点の本番 DB(`postgresql://…/ryza`)を数えた結果:

|---|---|
| `ledger.journal_entries` | **2 行**(`seed.initial_capital` / `seed.capital_increase` の出資仕訳のみ) |

| `ledger.nav_snapshots` | **0 行** |

出典: 2026-08-04 の `psql` 実測(本書起草時)。デモ執行は配線済みだが約定・評価替えの記帳実績はまだ無い。

### 4.2 コード移行

`securities` を参照する本番コードは 6 ファイル・約 40 箇所であり、うち意味を変える必要があるのは以下に限られる:

| ファイル | 変更 |

## 5. 採否

### 5.1 判断

採用する。移行コストの支配項(データ移行と全営業日の restatement)が**現時点でのみゼロ**であり、利得(§3.2 の恒等式)は運用が始まってからのほうが価値が高いという非対称があるためである。「現防御(`posted_by` 述語)で足りる」という結論は防御としては正しいが、**恒等式は現防御では書けない**ので、足りているのは攻撃面だけである。

### 5.2 反対意見書(この判断が間違っている場合の理由トップ3)

1. **分離は新-14 の攻撃を塞がない — 塞いだと誤読される危険のほうが大きい。** 分離後に `Dr securities_mtm 3,000,000 / Cr capital` を `posted_by='ledger.closing'` で立てれば、次の締めはその残高を「評価替えが作った残渣」と読んで全額洗い替え、NAV を同額落として偽の未実現損を立てる — 新-14 実測(a)と**同じ結果が同じ手順で再現する**。分離が変えるのは攻撃の宛先だけである。→ 対処: `posted_by` 述語を**外さない**(`post_mark_to_market` の検証と DB トリガの両方で残す)。本書はこの点を §7 に申し送る。
2. **保護領域の変更を「掃除」で正当化している疑い。** 得られるのは監査可能性であって不具合の修正ではなく、審査 1 回ぶんのコストと `migrations` の 1 本を消費する。→ 反論: 新-15(説明不能な残渣を誰も見ていない)は現に未解決の**検出漏れ**であり、恒等式はその根治である。掃除ではない。
3. **原価恒等式が偽陽性を出す可能性。** 約定以外で `securities` が動く正当な経路(現物拠出・資産振替・株式分割)が将来増えると、恒等式は毎日鳴る。→ 対処: 恒等式の真実側(`replay_position`)を**その経路ごと取り込む**のが正しい解であり、本 PR の現物拠出対応(新-17)がその第 1 例である。取り込めない経路が出た時点で恒等式は再設計する。

## 6. 実装範囲(本 PR)

1. `migrations/0034_ledger_mtm_account.sql` — `securities_mtm`(asset・`有価証券評価調整`)を **`book_type='fund'` の全帳簿**に追加。あわせて `journal_lines` に 2 本の書き込みガードトリガ:
   - **評価調整勘定**: `posted_by ∈ MTM_POSTED_BY` かつ `instrument_id NOT NULL`、または**実突合済みの逆仕訳**でなければ拒否
   - **原価勘定**(独立審査 新-20): `instrument_id NOT NULL` かつ親証憑の `kind ∈ POSITION_EVIDENCE_KINDS`、または実突合済みの逆仕訳でなければ拒否
2. `_util` / `posting` / `closing` の上記変更。
3. 現物拠出の数量再生(新-17)— `post_in_kind_contribution` と `in_kind_contribution` 証憑を新設し、`replay_position` の再生対象に含める。これは §5.2-3 の対処であり、原価恒等式の前提でもある。拠出は `posted_by ∈ IN_KIND_POSTED_BY` に限り、記帳と同一トランザクションで #運営 へ通知する(新-21)。
4. 対照テスト: 分離前後で NAV・日次リターン・`zero_qty_writeoffs` が一致すること(等価性)、新-10 / 新-13 / 新-14 / 新-16 の回帰テストが全て通ること。攻撃側は新-18(偽装逆仕訳)・新-20(instrument_id NULL の無言混入)の拒否を実測で固定する。

### 6.1 逆仕訳免除を「実突合」にした理由(新-18)

初版のガードは `reversal_of IS NOT NULL` という**フラグだけ**で免除していたが、`reversal_of` は `post_entry` の公開引数であり対象仕訳と突合されない。審査の実測では、無関係な `entry_id` を `reversal_of` に入れるだけで `posted_by` 検証を迂回して `Dr securities_mtm 3,000,000 / Cr capital` が通り、次の締めが全額を洗い替えて NAV 13,000,001→10,000,001・偽の未実現損 3,000,000 を立てた(新-14(a) の完全再現)。

是正後の免除条件は「その明細が、対象仕訳の同じ明細を打ち消しているか」の実突合である — 同一帳簿・同一勘定・同一銘柄で借方と貸方が入れ替わった行が対象仕訳に存在すること(`ledger.reversal_mirrors_line`)。`reverse_entry` が作る逆仕訳は厳密にこれを満たし、金額や銘柄を差し替えた「逆仕訳を騙る記帳」は落ちる。免除の範囲が「既にある記帳の取り消し」ちょうどになる。

### 6.2 原価勘定ガードを `posted_by` でなく `evidence.kind` で切った理由(新-20)

原価勘定の書き手は約定(`post_fill`)・現物拠出・締めの未記帳約定取り込みと複数あり、`posted_by` は呼び出し側ごとに違う(`ledger.posting` / `ledger.closing` / 執行系)。許可リストにすると広すぎるか正当な呼び出しを壊すかのどちらかになる。一方 `kind` は `replay_position` が数量を再生するときに見る値そのものなので、**ガードと恒等式が同じ定義を共有する**ことになり、「原価勘定に載る行は必ず数量再生の対象」という不変式が構造で保たれる。`posted_by` 側の統制は拠出 API(§6-3)に置いた。

## 7. 残る限界(申し送り)

- **`posted_by` も `evidence.kind` もアプリ層が決める値である。** DB トリガは「宣言し忘れ」と「うっかり」を止めるが、`post_entry` を呼べる者が値を騙る経路は残る。構造的に断つには DB ロール分離(締めジョブ専用ロール + `current_user` を見るトリガ)が要る。本書はこれを**採らなかった** — 単一ロール前提のインフラ全体に波及し、本件の利得に対して過大だからである(`ops/reminders.yaml` の申し送り対象)。
- **`securities_mtm` へ直接書く偽装は依然として NAV を双方向に動かせる**(§5.2-1・新-19)。原価恒等式はこの経路を**検出しない**。防御は `posted_by` 検証と DB トリガだけである。
- **恒等式は実在性の検査ではない**(新-21)。`post_in_kind_contribution` は証憑の数量・単価を呼び出し側の申告で書くため、架空の拠出でも恒等式は必ず成立し、しかも新-17 の是正により評価替えにも乗る。統制は `IN_KIND_POSTED_BY` の制限と #運営 通知(記帳と同一トランザクション)であり、どちらも**申告制の域を出ない** — 実在性は人が見る側での照合に委ねている。同じ限界は `broker_fill` を騙る申告にもあり、そのとき建玉は申告どおり再生されるため恒等式は「申告と帳簿の内部整合」として成立してしまう。
- **原価恒等式は「約定と拠出から見た原価」との一致しか見ない。** 株式分割・併合・現物払戻は未対応であり、原価勘定ガードが書込時に拒否する(fail-loud)。対応するときは証憑 kind を足して `replay_position` に再生を書く。
- **`post_fill` の売りが `as_of` 非対称**(新-22): `cost_released` を全期間再生で決めるため、後日付の約定が先に記帳された日は健全な帳簿でも `cost_identity_broken` が鳴る。毎日 #運営 に出る検査なので偽陽性は先に潰す — `ops/reminders.yaml` の `post-fill-asof-symmetry`。
- **LIVE_FUND の勘定 seed**(新-23): 本 migration の INSERT は適用時点の `book_type='fund'` に対する一回限りであり、将来 LIVE_FUND を 0006 の 18 科目で作ると最初の評価替えが `未知の勘定科目` で落ちる。実弾帳簿の初日に締めが落ちる設計にはしない — `mtm-account-live-fund`。
- **トリガと `MTM_POSTED_BY` の二重管理**(新-24): トリガは `'ledger.closing'` をハードコードしており、Python 側に 2 つ目を足すと DB が拒否する。単一ソース化は `mtm-posted-by-single-source`。
