# 08 — メタ監査規程(監査部門の監査)v1.0

**アーギュメント: 監査部門は自分自身の形骸化を検出できないため、監査コードの起草・審査・実装監査のいずれにも関与していない別系統の AI による四半期の外部品質評価(EQA)を制度化し、その実施をリマインダー・レジストリと証跡で強制する。**

制定根拠: `docs/design/00-system-design.md` §6「監査部門自体の更新機構」項2(年次メタ監査 = IIA 外部品質評価の移植)および同 §6 の営業期間圧縮(労働律速レビューの 年次→四半期)。A-12 監査所見 A-12-17(裁定 F-11・中、`docs/reviews/a12/00-adjudication.md` §3)が「実行基盤の未定義」を指摘したことによる是正。文書層は L3(`config/governance.yaml` document_layers — `docs/design/*.md` は L3)。

## 1. なぜ監査部門に監査が要るか

監査の最大の失敗モードは検出漏れではなく形骸化である。A-18 系の検査は毎週走って緑を返し続けるが、緑には二つの意味がある — 「違反がない」と「検査が違反を見なくなった」。閾値の緩み・免除リストの肥大・開示ノイズの常態化(警報疲れ)・同型所見の再発は、いずれも週次報告の見かけを変えずに監査の実効性を殺す。実務の内部監査がこの問題を外部品質評価(EQA: 独立した評価者による内部監査部門自体の評価。IIA 基準は最低5年に1回を要求する)で解くのに倣い、Ryza は AI 労働の速度に合わせ四半期で実施する(00-system-design §6 の圧縮判断: 月次化は12倍のコストで検出価値が見合わない)。

## 2. 独立性要件(実施者)

実施者は次のすべてを満たす AI エージェントとする:

1. **系統分離**: 監査部門コード(`src/ryza/audit/**`)の起草・独立審査・A-12 実装監査のいずれにも使われていないモデル系統を優先する。同一系統しか調達できない場合はその事実をレポート冒頭に開示する
2. **プロンプト分離**: 実施プロンプトには起草者・設計リード・ユーザーの選好や期待する結論を含めない(議論規約3の盲検と同型)
3. **自己評価の遮断**: 監査部門の自己申告(A-18 notes・docstring の限界開示)は読んでよいが、「監査は十分に機能している」という要約・評価文書を評価完了前に与えない

## 3. 入力(point-in-time で固定)

評価は実施時点のリポジトリ HEAD のスナップショットに対して行い、レポートに対象 SHA を記録する。標準入力セット:

- `src/ryza/audit/**` 全コード(検査項目の実装)
- `docs/design/00-system-design.md` §6・`docs/design/05-governance.md`(監査の設計上の責務)
- `config/governance.yaml`(protected_areas・controls — 検査対象の台帳)
- A-18 週次報告の履歴(週次ダイジェスト Issue)と `governance.decisions` の記録
- `docs/reviews/a12/`(直近の実装監査と裁定)および事故ポストモーテム
- `ops/reminders.yaml`(fired 履歴と放置エントリ)

## 4. 評価軸

**網羅性** — 設計文書が監査部門に割り当てた検査(A-1〜A-18)がコードとして実在するか。ゼロトレランス領域(帳簿分離違反/ゲート迂回/保護領域の無承認変更/証憑の欠損・改竄 — 00-system-design §6)のそれぞれに少なくとも1つの自動検査が対応しているか。protected_areas の登録漏れ(統制上保護すべきだが glob に載っていないパス)の探索。

**実効性** — 監査 KPI(指摘の検出→解消リードタイム・再発率・監査発の重要発見数)。直近四半期に A-18 が実際に検出した違反・滞留の実例。検査が fail-open に縮退した実行(verify 無効・dry-run)の頻度と開示の適切さ。

**形骸化** — 「懸念ゼロ」報告の連続(05-governance §形骸化の防止)。同型所見の再発(是正が対症で構造に届いていない兆候)。閾値・免除条件・許可リストの緩和履歴。恒常的な開示ノイズ(既知の sha_conflict 等)が新規警報を埋没させていないか。fired にならないまま放置されたリマインダー。

評価は「あら探しの件数」でなく**監査が今も痛い指摘を出せるかの判定**である。所見ゼロのメタ監査レポートは、それ自体を「反対すべき点を探して見つからなかった」と明示しなければならない(議論規約1)。

## 5. 出力と証跡

1. **レポート**: `docs/reviews/meta/<YYYY>-q<N>-meta-audit.md` に PR で保存する。front matter に `review` / `reviewed_sha`(対象 HEAD の40桁)/ `reviewer` / `review_date` / `verdict`(`effective` = 監査は機能している / `degraded` = 形骸化の兆候あり・是正要)を記録する。verdict は次のいずれかに該当すれば `degraded` とする: (a) ゼロトレランス領域のいずれかに対応する自動検査が存在しない、(b) 是正を要する所見のうち「重大」相当が1件以上ある、(c) §4 の形骸化兆候(懸念ゼロ連続・同型所見再発・閾値緩和・警報埋没・リマインダー放置)が2つ以上同時に観測される。判定基準に対する境界事例は実施者が理由付きで裁量判定し、レポートに明記する
2. **所見の追跡**: 是正を要する所見は GitHub Issue に起票し、レポートから参照する。裁定(採否)は設計リードが行い、A-12 裁定書と同じ形式で残す
3. **報告**: 結果は次回の経営会議(月次)で監査報告に含める
4. **実施記録**: `ops/reminders.yaml` の該当エントリを fired に更新し、完了時に次回分(+3ヶ月)を登録する。実施の証跡はレポートのコミット履歴と fired 履歴の両方に残る — どちらか一方の消去では実施偽装にならない

## 6. 制度の自己言及に関する注記

本規程自体も docs/design 配下の L3 文書であり、メタ監査の評価対象に含まれる(規程が緩められて EQA が骨抜きになる経路も、メタ監査が見るべき形骸化の一形態である)。本規程の改訂は document_layers の手続に従う(L3: 独立役員審査+#承認 通知後 48h 異議なしのみなし承認。定款第3条)。本規程の protected_areas への登録は次回 L1 バッチで行う(`ops/reminders.yaml` の `l1-protect-meta-audit-doc`)。
