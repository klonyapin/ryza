## F-8: ロール名 env の SQL 識別子検証(pass4-1)

### 問題

deploy-dashboard.sh はロール名(ダッシュボード用・バックアップ用等)を環境変数から受け取り、検証なしで SQL 識別子として埋め込む。operator 制御の env であり悪用経路は限定的(裁定どおり)だが、タイポや引用符・空白の混入が予期しない SQL になり得る。

### 実装

1. ロール名を SQL に埋め込む**全箇所の入口**で `^[a-z_][a-z0-9_]*$` の検証を行い、不一致なら理由と受け取った値(そのまま echo せず制御文字を除去して)を stderr に出して非ゼロ終了する
2. 検証は関数化して ops/lib/ に置く(pg_hba_check.sh 等の既存ライブラリの流儀に従う)。deploy-dashboard.sh 以外にもロール名 env を SQL に埋め込むスクリプトがあれば同じ関数を適用して報告
3. 長さ上限(PostgreSQL の識別子上限 63 バイト)も併せて検査

## F-13(lockfile): uv.lock のデプロイ資材化

### 問題

デプロイが lockfile を参照しない場合、本番の依存解決が CI(`--locked`)と乖離し得る。

### 実装

1. デプロイ系スクリプト(ops/ 配下)が Python 依存をインストールする箇所を特定し、`uv sync --locked`(または同等の lockfile 固定インストール)になっているか確認。なっていなければ是正し、uv.lock を配布資材(rsync 対象等)に含める
2. **デプロイスクリプトが依存インストールをそもそも行っていない場合**(手順書ベース等)は、コードを変えず、該当手順文書に lockfile 固定を明記する是正に留め、完了報告でその判断を明示する
