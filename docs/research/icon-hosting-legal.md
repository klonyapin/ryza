# キャラクターアイコンの再ホスト可否 — 再配布の法的整理

- 日付: 2026-08-04 / 起草: 実装エージェント(開発部門)
- 対象: `ops/reminders.yaml` の `icon-rehost-storage`(独立役員審査 0020 C-7 の恒久是正)が
  **着手前に整理せよ**と課した論点 — 「非公開の自前ストレージへの複製は、`config/org.yaml`
  冒頭が退けた『public リポジトリへの画像コミット』と同じ問題になるか」
- 位置づけ: 設計根拠(`docs/research/`)。**法的助言ではない**。実装判断を保守側へ倒すための
  内部整理であり、争点になれば弁護士の確認を要する(§7 に要検証項目を列挙する)

## 1. 結論

**アイコンは再ホストせず、ホットリンクを維持したまま定期再検証で差し替えを検知する。**

再ホストが退けられるのは著作権の一般論ではなく、**目的の側に公開配信が組み込まれている**
からである。0020 が解決しようとしているのは Discord embed のアイコン表示であり、Discord は
embed の `icon_url` を**自社サーバから取得**する。したがって「Discord に出す」構成は必ず
「誰でも取得できる URL」を伴い、私的複製の枠に留まらない。非公開ストレージに留める構成なら
公衆送信は避けられるが、その構成では Discord に出せず 0020 の目的を果たさない。目的を果たす
構成が法的に採れず、法的に採れる構成が目的を果たさない — この二律背反が結論を決めている。
リマインダー `icon-rehost-storage` は「整理の結果『再ホストしない』となった場合は定期再検証
ジョブを実装する」ことを明示的に許容しており、本稿はその分岐を選ぶ。

## 2. 事実確認 — いま何が、どこに置かれているか

**現行構成は自らのサーバに画像の複製を1バイトも持たない。**

`config/org.yaml` の 9 メンバー全員の `icon_url` は `https://safebooru.org/...` の外部 URL で
ある(2026-08-04 時点、リポジトリ内の台帳を確認)。リポジトリには `site/avatars/` が存在せず、
自前の画像素材は1点も無い。ダッシュボード(Streamlit)は `<img src=外部URL>` として代表の
ブラウザに読ませ、Discord は embed の `icon_url` を Discord 側が取得して配信する。DB
(`ops.org_icon_overrides`・0020)が持つのも URL 文字列だけである。

対象画像はアニメ作品のキャラクターを描いた第三者の二次創作であり、権利は少なくとも二層
(原作の著作権者と作画者)に及ぶ。safebooru は投稿型の集約サイトで、掲載画像が作画者の許諾を
得て転載されている保証はない。台帳の冒頭注記(`config/org.yaml` 3-5 行目)が「public リポジトリ
への画像コミットは再配布にあたるため行わず」と書いたのは、この構造を踏まえた判断である。
現行構成は、その判断と整合している。

## 3. 三つの構成と、それぞれが越える一線

**「複製するか」と「公衆へ送信するか」は別の権利であり、再ホストは前者だけでなく後者に触れる。**

| 構成 | 触れる支分権 | 評価 |
|---|---|---|
| (a) ホットリンク(現行) | なし | リンクは複製(21条)にも公衆送信(23条1項)にも当たらない |
| (b) 公開 GCS オブジェクト URL | 複製 + 送信可能化 | **不可**。私的複製は公衆送信を正当化せず、49条1項1号で複製時点に遡って侵害とみなされる |
| (c) 非公開 GCS + Bot がバイトを添付 | 複製 + (Discord CDN 経由の)送信可能化 | **不可に寄る**。Discord CDN の実体は認証を要しない配信であり「公衆でない」と言い切れない |
| (d) 非公開 GCS + ダッシュボードのみ | 複製 | 公衆送信は避けられるが **Discord に出せず 0020 の目的を果たさない** |

(a) を「侵害でない」と言える根拠は、令和2年改正が**リーチサイト規制(113条2項以下)を新たに
設けた**という立法事実そのものにある。リンクを張る行為が既に侵害なら、リンク集を規制する条文を
別に作る必要はない。裏を返せば、リンクは所在情報の提示であって著作物の利用ではない、というのが
立法者の前提である。

(b)(c) が越えるのは 23 条1項(公衆送信権 — 送信可能化を含む)である。ここで効かないのが 30 条
1項(私的使用のための複製)で、同条は**複製**の権利制限であって公衆送信を許すものではない。
さらに 49 条1項1号により、私的使用の目的で作った複製物を目的外に頒布・提示すれば、**複製した
時点で複製権を侵害したものとみなされる**。つまり「私的複製として作り、後で Discord に出す」は
制限規定の中では成立しない。

## 4. 30条1項そのものにも二つの障害がある

**仮に配信を非公開に閉じても(構成 d)、複製の側で二つの要件が引っかかる。**

第一に**業務性**である。30 条1項は「個人的に又は家庭内その他これに準ずる限られた範囲内において
使用することを目的とするとき」に限り、かつ「その使用する者が複製する」ことを求める。Ryza は
利用者が代表1名の非公開システムであり範囲の狭さは満たすが、資産運用という経済活動のための
システムであって、逐条解説が示す通説では**業務上の使用を目的とする複製は 30 条の私的使用に
当たらない**とされる。個人の資産運用が「業務」かは争いうるが、「争わずに済む領域」ではない。

第二に**取得元**である。30 条1項4号(令和2年改正・2021年1月施行)は、著作権を侵害する自動公衆
送信であることを**知りながら**行う複製を、私的使用であっても違法とする(軽微なものを除く)。
安全側に見れば、作画者の許諾関係が確認できない集約サイトからフル解像度の画像を取得して保存
する行為は、この除外に触れうる。**閲覧・表示は複製ではないため現行のホットリンクではこの論点が
そもそも生じない** — 保存した瞬間に生じる。

47 条の4(電子計算機における利用に付随する利用等 — いわゆるキャッシュ)による救済も検討したが、
同条は「当該利用を円滑又は効率的に行うために当該利用に付随する」複製を対象とする。本件の
複製目的は伝送の円滑化ではなく**改竄検知と外部アクセスの遮断**であり、付随性の説明が苦しい。
制限規定を目的外に引き伸ばして依拠するのは、保守側の判断ではない。

## 5. 採る構成 — 防止ではなく検知、そしてその限界

**C-7(保存後の差し替えに気づけない)は、防止が採れない以上、検知で扱う。**

実装は 0033(`ops.org_icon_checks` / `ops.org_icon_check_events`)と
`src/ryza/ops/icon_revalidate.py`。実効アイコン URL(台帳に 0020 の上書きを重ねた値)へ日次で
HEAD を投げ、`Content-Type` / `Content-Length` / `ETag` / `Last-Modified` の指紋を前回と比較し、
**同じ URL の中身が変わったとき**だけ #運営 へ報告する。URL 自体の変更は代表の意図した操作
(`ops.org_icon_override_log` に既に残る)なので再基準化し、通知しない。リマインダーは週次を
想定していたが日次にした — 検査は 9 件の HEAD にすぎず、通知は遷移があった日にしか出ないため、
頻度を上げても騒音は増えず検知から通知までのラグだけが7日から1日に縮む。

この検知は**誠実な配信元の差し替えしか捕まえない**。指紋は全て配信元が名乗るヘッダであり、
UA や IP で応答を出し分ける配信元には無力である。独立役員審査 0020 C-6 が「検証は UA 識別可能な
単発 HEAD で誠実な誤りしか防げない」と述べた限界は、周期的にしても消えない。これを塞げるのは
再ホストだけであり、法的整理により採らないと決めた以上、**受容した残存リスク**として明示する。
爆風半径は同審査が「中」と評価したとおり — 非公開サーバー・閲覧者は代表のみ・被害は代表 IP の
追跡と意図しない画像の表示に限られる。

なお、再ホストは C-6(SSRF)の解決策でもない。保存時に外部 URL の**本文まで**取得する経路を
作れば、現行(ヘッダのみ)より取得量が増え、検証時と取得時で名前解決が2回発生する DNS
rebinding の窓は残る。SSRF の根治は接続先 IP のピン留めであり、再ホストとは直交する論点である。

## 6. 反対意見書 — この判断が間違っているとしたらどこか

**議論規約(CLAUDE.md)に従い、本判断が誤りである場合の理由を三つ挙げる。**

1. **業務性の評価が過度に保守的かもしれない。** 個人が自分の資産を運用するための私物システムは、
   通説が想定する「法人の業務」ではないという整理は十分ありうる。それが通れば構成 (d)(非公開
   ストレージ + ダッシュボード表示のみ)は適法になる。ただし (d) は Discord に出せないため、
   仮にこの反論が正しくても**結論は変わらない** — 変わるのはダッシュボード側だけである。
   代替案: ダッシュボードの表示経路に限って (d) を採り、代表 IP の外部露出を消す。効果と
   実装量が釣り合わないと判断して見送ったが、IP 露出を重く見るなら再考に値する。
2. **「検知」は統制として弱いかもしれない。** クローキングに無力で、検知しても復旧は手作業で
   ある。「弱い統制を置いたから対処済み」と扱うと、05-governance §6-5 の形骸化そのものになる。
   代替案: 権利処理済み(自作・生成・委託)のアイコンへ差し替え、外部依存を根本から断つ。
   これが唯一の恒久解であり、本稿の判断は**その素材が用意されるまでの暫定**である
   (`ops/reminders.yaml` の `icon-own-artwork` に登録した)。
3. **法的リスクの見積もりが、実務上のリスクと乖離しているかもしれない。** 非公開サーバーで
   単一利用者しか見ない画像について権利者が現実に問題化する確率は低い。低い確率のために
   恒久是正を諦めた、という批判は成り立つ。反論としては、確率が低くとも**構成 (b) は
   条文上明確に不可**であり、確率論で越える種類の線ではない。

## 7. 要検証項目(法務確認が必要な点)

以下は本稿が**原典を参照せずに通説として扱った**箇所であり、争点化した場合に確認を要する。

- 30 条1項の「業務上の使用」除外の射程(出典: 加戸守行『著作権法逐条講義』30 条解説の通説。
  本稿執筆時に原典未参照)
- 個人の自動売買システムを「業務」と評価するかの実務的な線引き(判例を確認できていない)
- Discord CDN の URL(署名付き・有効期限あり)が「公衆送信」に当たるかの評価
- Discord 利用規約上の、アップロードするコンテンツについての権利表明保証との関係
